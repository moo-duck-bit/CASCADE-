# CASCADE Verifier 검사 규칙 v2

이 문서는 구현보다 먼저 고정한 검사 규칙이다. v1(V1~V6)에 Locator 판단과 독립인 검사 V2b·V3b·V6b를 더했다. 검사 대상 칸은 데이터셋의 정답 파일이 아니라 문서 구조(문서 종류, 항목 이름, 칸 이름, XXCS 열 이름, MDSR 6절 표 구조)와 요청에서 읽은 변경 내용으로만 정한다.
Verifier는 편집을 적용한 사본을 다시 파싱한 칸과, 원본 칸, 요청, Locator 결과(후보와 관련 판정), 편집 목록만 본다. 정답·연결표·사실 표·다른 검사기 코드는 보지 않는다.

출력은 지적 목록 `[{type, site, detail}]`이다. 지적은 "문제일 수 있음"이며, Editor는 확인 후 지적된 칸만 다시 고친다.

## 구조 정의

- 연결 칸: MDSR 6절 표의 `소프트웨어 기능 요구사항 번호` 칸, XXCS 시험결과 표의 `해당 요구사항` 칸. 칸 이름으로 정한다.
- 판단 칸: XXCS의 `체크리스트 적용 여부`, `체크리스트 입증 방법`(체크리스트 표 열 이름), `적용 여부`, `판정`(시험결과 표).
- Req 칸: MDSR Req 표의 칸, MDDR Req 번호 문단 아래 설계 문단. 항목 이름이 `Req. N`이다.
- 값 비교는 values.py 정규화(수치+단위, 한글 수사, 시각)를 쓰고, 숫자 없는 값은 공백·기호를 지운 비교를 쓴다.
  Verifier는 설정의 value_index 플래그와 관계없이 항상 정규화 비교를 쓴다(Locator의 값 색인을 꺼도 검사는 같다).
- 문서 이름·칸 이름은 도메인 팩에서 읽는다. 아래 이름은 EC-SW 팩 기준이다.
- Locator 의존 여부: V2·V5·V6은 Locator 결과(후보, 관련 판정)를 쓴다. V1·V2b·V3·V3b·V4·V6b는 쓰지 않는다.

## 검사

- V1 위치 존재: 수정(modify)·삭제 표기(mark_deleted) 편집의 위치가 원본에 없거나, 사본에 쓰지 못했거나, 추가(insert) 편집의 위치가 사본을 다시 파싱했을 때 나타나지 않으면 지적한다.
- V2 옛 값 잔존(T1): Locator가 관련으로 판정한 값 칸(origin, same_id, trace, value)의 사본 글에 옛 값이 남아 있으면 지적한다. 새 값이 옛 값을 포함하는 글(예: AES-256 → AES-256-GCM)은 새 값이 있으면 남은 것으로 보지 않는다. 같은 칸에 같은 숫자의 다른 사실이 있을 수 있으므로 지적은 확인 요청이다.
- V3 구조 결손(T3):
  - 삭제: 삭제 Req의 칸(번호 칸 제외)이 `삭제`가 아니거나, 사본의 어느 칸이든(삭제 Req 자기 항목 제외) 그 Req 번호를 아직 가리키면 지적한다.
  - 추가: 새 Req가 사본의 어떤 연결 칸에도 없으면 새 Req 번호 칸을 지적한다. 같은 보안 항목의 MDSR 연결 칸과 XXCS 연결 칸 중 한쪽에만 새 Req가 있으면(두 문서가 다 있을 때) 빠진 쪽을 지적한다.
- V4 규칙 불일치(T2, 규칙 표가 켜져 있을 때): 바뀐 속성 값으로 규칙 표를 다시 계산해, 규칙이 정하는 모든 보안 항목에 대해 사본의 판단 칸을 본다. 적용 여부 칸(두 종)이 계산 결과와 다르면 지적한다. 결과가 N/A인 항목의 입증 방법·판정 칸이 `해당 없음`이 아니면, 결과가 적용인 항목의 입증 방법·판정 칸이 `해당 없음`이면 지적한다.
- V5 범위 밖 수정(Locator 의존): 편집 위치가 Locator 후보에 없거나, 후보였지만 관련 없음으로 판정된 칸이면 지적한다.
  Locator 판단을 기준으로 삼으므로 Locator가 놓친 칸을 고친 편집도 지적된다. 단, 아래 V2b·V6b가 지적해 Editor가 확인한 칸은
  Verifier가 범위를 넓힌 것으로 보고 V5 대상에서 뺀다.
- V6 같은 사실 값 불일치(T1): 관련으로 판정된 값 칸(같은 사실로 판정된 칸들) 가운데 사본 글에 새 값이 없는 칸을 지적한다(다른 칸은 새 값으로 바뀌었는데 이 칸만 다른 값이 되는 경우 포함).

- V2b 옛 값 잔존, Locator 독립(T1): 검사 범위는 출발 Req 항목의 모든 칸(번호 칸 제외), 다른 문서의 같은 번호 항목의 칸,
  출발 Req와 trace로 연결된 연결 항목의 모든 칸(MDSR 6절 행, XXCS 체크리스트·시험결과 행)이다. 이 범위의 사본 글에 옛 값(정규화)이
  남아 있으면 Locator 판정과 관계없이 "확인 필요"로 지적한다. V2와 같은 칸이면 V2만 낸다.
- V3b 구조 결손, Locator 독립(T3): 연결 칸은 문서 구조(팩의 link_cells)로만 정한다.
  - 추가: 새 Req가 추가된 문서(req_docs 가운데 앵커가 있는 문서)에 새 Req 번호 칸이 사본에서 읽히지 않으면 지적한다.
    같은 연결 항목의 연결 칸이 두 문서 이상 있을 때 한쪽에만 새 Req가 있으면 빠진 쪽을 지적한다(v1 V3과 같은 규칙을 Locator 없이).
  - 삭제: 삭제 Req 번호가 사본의 어느 연결 칸에든 남아 있으면 지적한다.
  V3과 같은 칸이면 V3만 낸다.
- V6b 같은 값 미편집, Locator 독립(T1): 원본에서 옛 값과 정규화 값이 같은 칸(값 색인, 숫자 없는 값은 느슨한 비교) 가운데
  편집되지 않았고 V2b 범위 밖인 칸을 "같은 사실인지 확인"으로 지적한다. 같은 숫자의 다른 사실일 수 있으므로 확인 요청이다.

## 피드백 원칙

- 피드백 문장은 v1과 같다: "아래 지적은 문제일 수도 아닐 수도 있다. 확인 후 지적된 칸만 수정하고, 나머지 편집은 그대로 유지한 최종 JSON을 출력하라."
- V2b·V6b가 지적한 칸이 Editor의 고칠 칸 목록에 없으면 그 칸을 현재 글과 함께 목록에 더해 준다. Editor가 글을 바꾸지 않으면
  편집으로 치지 않는다(원문과 같은 글의 편집은 버린다).

## 대조군

- fake_feedback 모드: 실제 검사로 지적 수 n과 유형별 개수를 센 뒤, 같은 유형 개수만큼 이 케이스의 칸 가운데 무작위 위치(시드 = 설정 시드 + 케이스 id + 라운드)로 같은 형식의 지적을 만든다. 실제 지적 내용은 쓰지 않는다.

## 고리에서의 쓰임

- 지적이 있으면 지적된 칸만 다시 고친다(최대 K회). 멈춤: 지적 없음 / 편집 변화 없음 / 같은 지적 반복 / 토큰 예산 초과.
- 게이트는 마지막 상태에서 V1·V5 지적이 남은 편집을 칸 단위로 되돌리고, 그 뒤 V3·V3b 지적 수를 구조 결손, V6 지적 수를
  일관성 회귀 수치로 기록한다.
- 편집 연산(edit_mode=ops)의 실행 오류는 검사가 아니지만 같은 피드백 메시지에 traceback 형식으로 함께 넣는다.

## 변경이 여러 개인 요청(v0.3 전 추가)

- 속성 여러 개를 함께 바꾸는 T2 요청은 변경 하나로 검사한다. V4는 요청의 속성을 모두 새 값으로 둔 상태에서 규칙 표를 다시 계산한다.
- '… 또한 …' 복합 요청은 변경마다 따로 검사 고리를 돈다. 각 고리는 그 변경의 편집만 원본에 적용한 사본을 본다.
- 게이트는 변경마다 V1·V5 롤백을 한 뒤 편집을 요청 순서대로 합친다(같은 칸은 앞 변경의 편집). 마지막 수치는 합친 사본을 읽되
  변경마다 그 변경이 남긴 편집만으로 검사해 더한다.

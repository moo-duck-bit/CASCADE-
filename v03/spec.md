작성 2026-11-02. 근거는 reports/final_report.md의 "v0.3 데이터 수정 사항" 5개와 사용자 지시(2026-11-02)다.
이 문서를 먼저 고정하고 생성을 시작한다. 생성 결과를 보고 규격을 바꾸지 않는다. 바꿔야 하면 아래 "변경 기록"에 날짜와 이유를 남긴다.

## 1. 범위

- 제품당 케이스 60개: T1 값 변경 24, T2 규칙 재계산 12, T3 요구사항 변경 24(추가 14 중 복합 6, 삭제 10).
- 제품: P1 수면코치(v0.2 제품을 키운 것), P2 아동 ADHD 주의력 게임, P3 성인 금연 코치. 이번 단계는 P1의 사실 표와 문서 3종, 케이스 선택 시트까지만 만든다. P2·P3는 products/P2·P3/profile.md 사양 카드만 둔다.
- v0.2 데이터(pilot_data/product, docs, cases)는 그대로 둔다. v0.3 산출물은 모두 pilot_data/v03 아래에 둔다.

## 2. 형식 (v0.2와 동일, scorer·verifier 호환)

- 문서 3종: MDSR(요구사항명세서), MDDR(설계명세서), XXCS(소프트웨어 보안검증보고서). 템플릿은 pilot_data/templates의 사본 3종을 그대로 쓴다.
- 위치 표기: "[문서 | 항목 | 칸]", 여러 문단 칸은 "#p1, #p2 …". 위치를 붙이는 코드는 v0.2와 같은 lib/ 코드를 쓴다.
- 정답 파일: v02와 같은 cases/<id>/gold/impact.json(items, neutral, change), must_not_touch.json(items). 필드 이름과 경로 라벨(origin, same_id, trace, same_value, rule)은 v0.2와 같다.
- 요청 문형: 구조화 요청은 v0.2 문형을 따른다.
  - T1: "{Req} '{제목}'의 {사실 이름}을 {옛 값}에서 {새 값}으로 변경한다."
  - T2: "제품 사이버보안 속성 '{속성 이름}'({속성})을 {옛 값}에서 {새 값}로 변경한다. 첨부3 적용 예외에 따라 문서를 갱신한다."
  - T3 추가: "{구성요소} 요구사항 {Req} '{제목}'을(를) 신규 추가한다. 내용: {설명}"
  - T3 삭제: "{Req} '{제목}' 요구사항을 삭제한다. 요구사항 번호는 유지하고 '삭제'로 표기한다."
  - 자연어 요청 문장도 v0.2처럼 함께 만든다.
- 한 가지 바뀌는 형식: MDSR 각 Req의 "기준" 칸은 모든 Req에서 정확히 2문단(기준#p1, 기준#p2)으로 고정한다(최종 리포트 v0.3 수정 사항 3). T3 추가 케이스의 새 Req도 기준 2문단으로 만든다. 칸 단위 과수정에 기준 줄 수 차이가 섞이지 않게 하려는 것이다.

## 3. 제품 규모 목표 (P1)

- 사실 35~45개. 같은 값 묶음은 단위까지 같은 짝만 인정하고 6쌍 이상.
- 요구사항: 앱 Req. 1~18, 서버 Req. 100~108(27개). 보안 요구사항이 아닌 Req가 10개 이상이어야 하고, 그중 10개 이상은 6절 연결이 1개 이상 있어야 한다(삭제 케이스에 trace 정답이 생기도록).
- 사이버보안 속성 7개, 규칙(첨부3 적용 예외) 10개. 한 보안 항목은 한 규칙에만 속한다.
- 사실 배치: 바뀌는 사실이 연결된 XXCS 행 2개 이상에 들어가는 사실이 12개 이상(T1 trace용).

## 4. 경로와 유형 분리

- T1 24개 중 12개 이상은 바뀌는 사실이 출발 Req와 relevant로 연결된 XXCS 행 2개 이상에 들어가는 케이스로 고른다. 이 케이스는 XXCS를 입력 문서에 포함해야 한다.
- T3 추가 14개 중 6개는 복합 케이스다. 새 Req 추가와 함께 사실 값 변경(same_value 경로가 나오게) 또는 사이버보안 속성 변경(rule 경로가 나오게)을 같은 요청에 넣는다. 복합 6개 중 값 변경 동반 3개, 속성 변경 동반 3개를 목표로 한다.
- 경로가 유형에 묶이지 않게 하는 것이 목적이다. 파일럿에서는 trace가 T3, rule이 T2에만 몰려 경로 효과와 유형 효과를 나눌 수 없었다.

## 5. same_value 정답

- P1 전체 케이스에서 same_value 경로 정답 칸이 35칸 이상이어야 한다(파일럿 33칸).
- same_value 정답은 바뀌는 사실이 출발 Req 밖에 놓인 칸이다: 같은 사실을 쓰는 다른 Req의 MDSR·MDDR 칸, MDSR 3.4 일반적 제한, 출발 Req와 relevant로 연결되지 않은 XXCS 행.
- 같은 값이지만 다른 사실(같은 값 묶음의 짝)이 놓인 칸은 함정(must_not_touch, path same_value)이다.
- 이를 위해 사실 표에서 여러 Req가 함께 쓰는 사실을 10개 이상 둔다.

## 6. 과연결 비율

- 6절 연결 중 relevant=false 비율은 0.5로 둔다. 실제 인허가 문서의 판정 결과가 없어 보정하지 못한 값이므로 products/P1/product/links.json과 시트에 "미보정"으로 표시한다.
- 생성 방식: 보안 항목마다 relevant 연결 수를 정하고 relevant=false 연결을 같은 수만큼 둔다. 그래서 비율은 정확히 0.5가 된다.

## 7. 보안 약화 금지

아래 변경은 케이스로 만들지 않는다. case_spec.csv 작성 기준에도 같은 목록을 둔다.

- 보안 요구사항 삭제. 보안 요구사항은 보안 사실(로그인, 잠금, 세션, 비밀번호, 암호화, 감사로그, 백업 등)을 쓰거나 보안 기능 자체를 정의하는 Req다. req_list.csv에 "삭제 금지"로 표시한다.
- 보안 값을 약하게 바꾸는 값 변경:
  - 로그인 실패 허용 횟수 늘리기
  - 계정 잠금 시간 줄이기
  - 세션 종료 시간 늘리기
  - 비밀번호 최소 길이 줄이기, 조합 규칙 완화
  - 더 약한 전송·저장 암호 방식
  - 감사로그 보관 기간 줄이기
  - 백업 주기 늘리기
  - 그 밖에 사실 표의 stronger_when(강해지는 방향)과 반대인 변경
- 보안 기능을 끄는 방향의 T2:
  - password_auth true→false(비밀번호 인증 제거)
  - session_termination true→false(세션 종료 기능 제거)
  - 그 밖에 cyber_attrs.csv에서 "약화"로 표시된 방향
- 허용되는 T2는 기능이 늘어나 보안 항목이 새로 적용되는 방향이다(N/A→적용). 예: 개인식별정보를 저장하게 됨, 원격 업데이트 기능 추가.

## 8. 문서 수 균형

- 유형마다 엮인 문서 수 1·2·3의 비율을 각각 1/3 ±10%p로 맞춘다(24개면 각 6~10개, 12개면 각 3~5개).
- 가능하면 같은 변경을 문서 조합만 달리해 배치한다(최종 리포트 v0.3 수정 사항 2). 문서 수 효과와 정답 범위 효과를 나누려는 것이다.
- T1·T3는 MDSR을 항상 포함한다(출발 칸이 MDSR에 있음). T2는 XXCS를 항상 포함한다(rule 정답이 XXCS에 있음).

## 9. 정답 규칙

정답 규칙은 첨부3 적용 예외 조항과 문서 구조로만 정의한다. verifier/ 코드와 Verifier가 고르는 칸은 참고하지 않는다(최종 리포트의 독립성 지적).

- T1 값 변경
  - 정답(impact): 입력 문서 안에서 바뀌는 사실(과 depends_on으로 파생되는 사실)이 놓인 모든 칸.
  - 경로: 출발 Req의 MDSR 칸은 origin, MDDR의 같은 Req 칸은 same_id, 출발 Req와 relevant로 연결된 XXCS 행은 trace, 나머지는 same_value.
  - 함정: 같은 값 묶음 짝의 칸(same_value), 출발 Req와 relevant=false로 연결된 적용 XXCS 행의 확인결과 칸(trace).
- T2 규칙 재계산
  - 정답: 뒤집힌 속성이 정하는 보안 항목에서 판단이 실제로 바뀌는 XXCS 칸 4종만(체크리스트 적용 여부, 체크리스트 입증 방법, 결과표 적용 여부, 판정).
  - neutral(채점 제외): 같은 행의 나머지 칸(비고, 해당 요구사항, 시험방법, 확인결과)과 MDSR 6절 연결 칸.
  - 새 값: 적용→N/A면 적용 여부 "N/A", 판정·입증 방법 "해당 없음". N/A→적용이면 적용 여부 "적용", 판정·입증 방법은 시험 전이라 null.
  - 함정: 다른 속성의 규칙이 정하는 항목의 적용 여부 칸.
- T3 추가
  - 정답: 새 Req의 MDSR 칸(번호, 제목, 설명, 목적, 기준#p1, 기준#p2; op=insert), MDDR 설계 칸(same_id; op=insert), 관련 보안 항목의 MDSR 6절 연결 칸과 XXCS 해당 요구사항 칸(trace).
  - 복합 케이스는 위에 T1(값 변경) 또는 T2(속성 변경)의 정답을 더한다. 경로 라벨은 각 규칙을 그대로 따른다.
  - 함정: 같은 분류지만 새 기능과 무관한 보안 항목의 연결 칸.
- T3 삭제
  - 정답: 삭제 Req의 MDSR 칸(번호 제외, "삭제"), MDDR 설계 칸(same_id), 그 Req와 연결된 적용 보안 항목의 연결 칸(trace, Req 번호 제거).
  - 함정: 뒤 번호 Req의 번호 칸(재정렬 금지).
  - 보안 요구사항은 삭제 대상에서 뺀다(7절).

## 10. 생성 모델

- 지정 모델은 EXAONE-4.0.1-32B였다. 공개본이 BF16(64GB)뿐이고 공용 서버의 쓸 수 있는 디스크 여유가 66GB라 받을 수 없었다. 사용자 지시(2026-11-02 "일단 Qwen 받아놓은걸로")로 Qwen3-32B-FP8(파일럿과 같은 모델, revision aa55da1)로 생성한다.
- 경고(동일 계열): 데이터 생성 모델과 평가 대상 모델(B1·B2·B3·Verifier의 Qwen3-32B)이 같은 계열이다. 생성 모델의 표현 습관이 평가 모델에 유리하게 작용할 수 있다. 본실험 보고 시 이 점을 한계로 적고, 가능하면 다른 계열 모델로 만든 제품(P2 또는 P3)과 결과를 비교한다.
- 사실 값, 요청 문장, 정답은 코드가 정한다. LLM은 사실 후보, 배치, 요구사항 제목·사용 사실, relevant 연결 선택, 문서 본문 문장만 만든다. 모든 호출은 v03/runs/gen_log.jsonl에 남긴다.
